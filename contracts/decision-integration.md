# Граница backend ↔ decision

Пакет `decision/` добавлен в общий репозиторий как независимый слой правил и оценки. Его можно установить и тестировать вместе с backend. **Адаптер между двумя внутренними контрактами пока не реализован; добавление пакета не подключает ML и не меняет поведение адаптера `unavailable`.**

Документы другой части команды: [decision/README.md](../decision/README.md), [docs/ml-integration.md](../docs/ml-integration.md). Действующие интерфейсы worker: [contracts/README.md](README.md), [VideoIO](video_io.md).

## Различия контрактов

| Область | Backend сейчас | Decision сейчас | Что требуется согласовать |
|---|---|---|---|
| Вызов анализатора | Фабрика без аргументов → `analyze(context, video)` | В документации observer предложен `analyze_video(video_path, job_id, deadline_at, profile)` | Wrapper должен принимать переданный общий `VideoIO`; сам пакет decision не реализует observer |
| Результат анализатора | `ObservationBatch(complete, events, diagnostics)` | `Observation(video_id, duration_sec, analysis_status, coverage_complete, candidates)` | Источник идентификатора видео и длительности, сохранение сведений о завершении/покрытии |
| Интервал | `t_start`, `t_end`, `t_main` | `start_sec`, `end_sec`, `main_sec` | Явное преобразование имён без изменения времени |
| Идентичность кандидата | Отдельного поля нет | Обязательный `candidate_id` | Стабильная идентичность и сохранение происхождения кандидатов |
| Наблюдения | `observations` со значениями `observed/not_observed/unclear` | `predicates` с теми же тремя состояниями | Совпадающий словарь имён предикатов и их смысл |
| Видимость | Пообъектные `clear/partial/unusable` | Именованные условия видимости со значениями `observed/not_observed/unclear` | Это разные утверждения; автоматического преобразования enum нет |
| Источник | Список `sources`: `vlm/motion/detector` | Строка `source`, включая версии или несколько имён через `+` | Перечень поддерживаемых источников и отдельное сохранение версии/диагностики |
| Кадры | `frame_pts`, реальные времена общего декодера | `EvidenceRef(frame_id, pts_sec, source)` | Стабильная таблица ID → видео/PTS/источник; байты не помещаются в наблюдения |
| Применение правил | `evaluate(batch, context) -> list[RuleEvent]` | `decide(observation, rules) -> DecisionResult` | Фабрика wrapper, передача всех обязательных данных и проверка статуса |
| Выход | Backend сам собирает официальный `JobDone` | Есть отдельный `to_public_payload` с `VerifiedJPEG` | В текущем сервисе окончательный ответ собирает только backend |

Например, `clear` для кассового рабочего места не подтверждает условие `all_possible_client_positions_visible`. Нельзя заменить его на `observed` только из-за сходства названий. Аналогично, отсутствующее поле не означает `not_observed`. Времена нельзя восстанавливать по условным 30 FPS или по порядку кандидатов.

## Безопасное подключение

1. Согласовать единый вход observer и правила преобразования **до** настройки `FORTE_ANALYZER_FACTORY` / `FORTE_RULES_FACTORY`. Сейчас ни один из модулей `forte_decision` не предоставляет эти две фабрики. Внутренние схемы строгие, поэтому отправка объекта одного формата напрямую в другой завершится ошибкой.
2. Wrapper анализатора получает `context` и тот же `video`, который уже проверен worker. Длительность и PTS берутся из `video.probe()`. Все обращения к кадрам проходят через этот объект. Слой decision сам не декодирует видео и не конфликтует с владением `VideoIO`.
3. Сохранить video/candidate/frame IDs и версию источника в согласованном контракте адаптера. Текущий `ObservationBatch` не содержит всех полей `Observation`; нельзя молча выбросить их или подставить выдуманную длительность. При необходимости версионировать внутреннюю схему вместе с обеими командами, сохранив внешний API жюри.
4. Преобразовать завершённость без послаблений: только `analysis_status == "complete"` **и** `coverage_complete is True` могут соответствовать `complete=True`. Статус `partial`, `failed`, `incomplete`, исключение или незавершённый профиль приводят к `failed`, а не к отрицательному verdict. Пустой список событий не подтверждает выполнение анализа.
5. Wrapper правил вызывает существующий `decide`; он не создаёт собственную классификацию и не подменяет каталог. `DecisionResult.status` обязан быть `complete`. Из каждого `Event` готовится `RuleEvent`, а поля нормативного источника берутся из той же версии каталога по `rule_id`.
6. Backend повторно проверяет интервалы, реальные PTS и 1–3 доказательства; извлекает JPEG через общий `VideoIO`, кодирует base64 и сохраняет `JobDone`. Не вызывать `to_public_payload` как второй serializer в этой цепочке. Его `VerifiedJPEG` — утверждение вызывающей стороны о проверке байтов, а не декодер или доказательство валидности JPEG.

Для преобразования нормативных полей используются `Rule.source_document` → `RuleEvent.rule_title`, `source_paragraph` → `rule_section`, `source_url` → `rule_url`; `rule_id` и `type` сохраняются. `Event.description` уже включает ссылку на норму, а backend добавляет её при сериализации: адаптер должен согласовать фактическое описание и отдельные поля источника, чтобы избежать повторов. Нельзя удалять ссылки ненадёжным разбором произвольной строки.

Есть и различие в таймкоде: decision сохраняет выбранный `main_sec` кандидата, backend привязывает итоговый `timecode_sec` к ближайшему кадру из доказательств. При адаптации это нужно явно проверить и документировать; передаваемые `frame_pts` должны точно соответствовать временам `VideoIO`.

В JSON-файлах каталога и наблюдений использовать явное `encoding="utf-8"`, особенно на Windows. Ключи, видео, кадры и содержательные наблюдения не должны попадать в диагностические логи.

## Совместная проверка после адаптации

Пакет decision не требует GPU или дополнительного runtime. Из корня репозитория:

```bash
python -m pip install -c requirements.lock -e '.[dev]' -e './decision[dev]'
python -m pytest backend/tests decision/tests data_tools/test_inventory.py rules/test_catalog.py
```

На Windows можно использовать `.\.venv\Scripts\python.exe` вместо `python`. Общие тесты используют синтетические данные и не подтверждают качество распознавания, полноту каталога или скорость реальной модели.

Для будущего адаптера нужны проверки обоих verdict, нескольких событий, сохранения идентичности кадров/PTS, неизвестных предикатов, несовместимой видимости и неполного анализа. После них — реальный прогон с локальным observer и замеры общего времени. Пока адаптера нет, установка `decision/` полезна для независимых тестов правил и evaluator, но сервис продолжает требовать собственные рабочие фабрики.

Текущий Dockerfile включает backend и contracts. Для runtime-подключения decision нужно отдельно включить его пакет и используемый каталог правил в образ; установка decision в CI не изменяет состав Docker-образа.
