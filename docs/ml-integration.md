# ML → правила → API

Канонический контракт сервиса — backend **ObservationBatch** из backend/contracts.py. Реализована фабрика `forte_decision.backend_adapter:create_rules`, принимающая этот контракт и AnalysisContext. Старый Observation остаётся внутренним форматом автономного CLI и тестов decision, а не вторым wire-форматом сервиса.

## Установка и запуск

Из корня репозитория, Python 3.11+:

```sh
python -m pip install -c requirements.lock -e '.[dev]' -e './decision[dev]'
python -m pip install -r data_tools/requirements.txt
export FORTE_RULES_FACTORY=forte_decision.backend_adapter:create_rules
export FORTE_RULE_CATALOGS='["rules/cash_receipt.json"]'
```

На Windows задайте переменные средствами своей оболочки. При запуске вне корня используйте абсолютные пути каталогов. Editable checkout также находит seed-каталог автоматически; при установке wheel задайте FORTE_RULE_CATALOGS явно. Каталог проверяется при создании фабрики.

FORTE_ANALYZER_FACTORY должен указывать на реальную фабрику vision с методом `analyze(context, video) -> ObservationBatch`. Observer использует переданный [VideoIO](../contracts/video_io.md), а не второй независимый декодер. Rules-фабрика не заменяет модель; development unavailable остаётся ошибкой.

## Реализованная граница

Rules-фабрика не читает видео и не придумывает длительность. Worker проверяет границы, реальные PTS, извлекает исходные JPEG и собирает официальный JobDone. Rules возвращают list[RuleEvent]. Времена не пересчитываются через FPS. Идентичность кадров основана на job ID и PTS; идентичность кандидата — на содержимом. Backend привязывает публичный таймкод к ближайшему из выбранных 1–3 кадров.

RuleEvent.description содержит буквальное описание каталога без ссылки. Документ, пункт и URL передаются отдельными полями; только backend добавляет их в публичный description. Второй serializer to_public_payload здесь не вызывается. Он сохранён для автономного использования; отсутствующий кадр в карте теперь вызывает ValueError.

## Политика review

- Два ключевых признака seed-правила observed дают возможное нарушение при неясной видимости/контексте. Описание условное и требует проверки человеком.
- Явный not_observed ключевого признака или применимости отклоняет правило; установленное исключение тоже.
- Неясный ключевой признак или исключение остаётся неразрешённым. Без положительных событий rules вызывает IncompleteAnalysis; worker выдаёт failed, а не чистый отрицательный ответ.
- Положительное событие сохраняется при других неразрешённых кандидатах, если анализ видео завершён. complete=False всегда означает незавершённый анализ.
- complete=True с пустым events допускает отрицательный ответ только как утверждение observer о выполненном анализе. Не удаляйте подозрительные неразрешённые кандидаты перед передачей.
- Положительный признак без покрытия каталогом остаётся неразрешённым. Одно движение или число уверенности не создаёт выдуманную норму.

Это дискретная политика первичного отбора, не калиброванная вероятность. Пороги модели и полноту типов проверяем на данных. Strict оставлен для сравнения и аудита.

Пообъектная видимость clear/partial/unusable остаётся поддержкой оценки. Partial, отсутствие оценки или неясный контекст не являются общим запретом. Если все указанные объекты unusable, кандидат неразрешён. Clear для кассира не доказывает полную видимость всех позиций клиента. Именованные условия обзора передаются в observations как явно проверенные tri-state предикаты и не выводятся из enum.

## Первый реальный замер

Импорт XLSX и gold.json описаны в [data_tools](../data_tools/README.md). Типы сначала размечает локальная модель, затем проверяет человек. Видео, кадры, реальные наблюдения и описания остаются локально; передаются только агрегаты.

```sh
python -m data_tools.evaluate_service --base-url http://127.0.0.1:8000 \
  --videos /path/videos --gold local_data/gold.json \
  --output-dir local_data/evaluation --limit 5
```

Ключ читается из FORTE_API_KEY. Уберите --limit после первого smoke для полного набора. Инструмент сохраняет результаты локально, stdout содержит агрегаты завершённости, ошибок, бинарных метрик, времени и попаданий по таймкодам. Ошибки и таймауты учитываются как пропуски в end-to-end recall и как неуспехи в общей accuracy. Без исчерпывающей разметки событий event precision не заявляется. Первый проход по открытому набору — development baseline, не отложенный тест.

## Проверка подключения

```sh
python -m pytest -q backend/tests decision/tests data_tools rules/test_catalog.py
```

FFmpeg/ffprobe должны быть в PATH либо заданы в FORTE_FFMPEG_BIN/FORTE_FFPROBE_BIN. Тесты decision используют синтетическое видео, настоящий worker/VideoIO и декодирование JPEG. Они проверяют интеграцию, не качество VLM. Реальный baseline публикуется только после запуска реальной модели.

Docker пока требует включения decision, каталога, runtime vision и локальных весов; нативная установка выше уже поддерживает rules-фабрику. Сам факт наличия пакетов не означает готовность analyzer.

## Локальный аудит пропусков

Перед запуском worker можно задать `FORTE_LOCAL_AUDIT_DIR` на приватный локальный каталог. Observer запишет там наблюдения и интервалы кандидатов до/после отбора; файлы имеют хешированные имена и права 0600. Это содержимое не предназначено для коммита или передачи внешним AI. Без переменной аудит выключен.

После HTTP-прогона:

```sh
python -m data_tools.aggregate_failures \
  --predictions local_data/evaluation/predictions.json \
  --gold local_data/evaluation/gold_subset.json \
  --inventory local_data/inventory.json \
  --output local_data/evaluation/aggregate.json
```

Вывод разделяет пропуски завершившегося классификатора и положительные видео, потерянные из-за ошибки выполнения. Метрики взвешивают все файлы; число уникальных SHA и конфликты дубликатов указаны отдельно. Точное и допустимое совпадение таймкодов считаются независимо. Latency p50/p95 остаётся в исходном `report.json` и включает все попытки.
