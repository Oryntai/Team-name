# ML → правила → API

В проде работает анализатор «по якорям»: `FORTE_ANALYZER_FACTORY=forte_vision.anchored.analyzer:create_analyzer`, код — `vision/src/forte_vision/anchored/`. Для жюри он описан в [SUBMISSION.md](SUBMISSION.md): запуск — §2.3, архитектура и проверки — §3, ограничения и замеры — §7. Здесь только граница «анализатор → правила → worker» и офлайн-замер.

Канонический контракт сервиса — **ObservationBatch** из `backend/contracts.py`. Старый Observation остаётся внутренним форматом автономного CLI и тестов decision, а не вторым wire-форматом сервиса.

## Цепочка одного задания

`backend/worker.py`, `_analyze_job`:

1. **VideoIO** (`ffprobe`) проверяет файл и отдаёт длительность и список настоящих PTS.
2. **Анализатор** `analyze(context, video) -> ObservationBatch`. Кадры для детектора и вырезок он читает сам через PyAV. Переданный VideoIO даёт длительность и канонические PTS: к ним анализатор прижимает таймкод и кадры каждого события (`VideoIOSource.snap`). Каждое событие — `ObservedEvent` с одним предикатом в состоянии `observed` (например `safe_left_open`), интервалом, главным моментом и 1–3 `frame_pts`.
3. **Worker** проверяет, что события не выходят за длительность и что каждый PTS есть в списке ffprobe.
4. **Правила** `forte_decision.backend_adapter:create_rules` возвращают `list[RuleEvent]`: тип, описание из каталога, `rule_id`, «документ — название», пункт, ссылку и кадры. События одного правила с пересекающимися интервалами и главными моментами в пределах 1 с сливаются в одно; кадров — до трёх, ближайших к главному моменту.
5. **Worker** извлекает JPEG ровно по этим PTS через VideoIO (ffmpeg). Публичный `timecode_sec` — PTS того кадра события, что ближе всех к главному моменту. В `description` добавляется строка «Нормативное основание: документ — название; пункт (ID: …). URL». Норма приходит отдельными полями RuleEvent, и backend добавляет её один раз.

Времена не пересчитываются через FPS. Rules-фабрика не читает видео и не придумывает длительность.

## Предикаты и каталог

- Таблица «проверка → предикат» — `anchored/decide.py`, `PREDICATE`. Анализатор выдаёт предикат, только если он стоит в `required` хотя бы одного правила загруженного каталога. Поэтому проверка KEYS («ключ в замке сейфа») молчит: такого правила в `rules/cash_checks.json` нет.
- Каталог задаёт `FORTE_RULE_CATALOGS` (JSON-массив путей), по умолчанию `["rules/cash_checks.json"]`. Анализатор считает относительные пути от корня репозитория, decision — от текущего каталога. Поэтому при запуске вне корня пути нужны абсолютные. Оба читают каталог при старте процесса модели, decision заодно проверяет его схему.
- В текущем каталоге 13 правил. У каждого один ключевой предикат и нет условий применимости, исключений и требований видимости. Схема «по якорям» выдаёт 10 из них, перечень — [SUBMISSION.md](SUBMISSION.md) §6.

В decision остаётся общий механизм: состояния `observed / not_observed / unclear`, «неразрешённые» кандидаты, режим `strict` для аудита. Анализатор «по якорям» его не задействует. Он отдаёт только подтверждённые события, все с `observed` и без пообъектной видимости. Сомнение остаётся внутри анализатора: ответ модели «unclear» не считается за «да».

## Когда `failed`, а не «чисто»

- **Анализатор вернул `complete=False`** (`anchored/analyzer.py`, `trustworthy`). Это бывает, только если ничего не найдено и при этом выполнено одно из условий:
  - на все заданные вопросы сервер модели вернул ошибку;
  - запрос зон сорвался и ни одного вопроса по вырезкам не задано;
  - моменты для проверки были, но до срока не задан ни один вопрос;
  - сорвалась половина вопросов по событиям или больше.

  Worker поднимает `IncompleteAnalysis`, задание получает `failed`.
- **Найдено хотя бы одно нарушение** — вердикт `violation`, даже если часть вопросов не успели задать.
- **Другие причины `failed`:** истёк срок, файл не декодируется, PTS не из списка ffprobe, процесс модели не стартовал или упал. Код причины хранится только во внутренней базе, в публичном ответе его нет.

## Настройки анализатора

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `FORTE_VLM_URL` | `http://127.0.0.1:18080` | OpenAI-совместимый сервер модели (`llama-server`). Разрешены только localhost, частная сеть и `.local`, иначе анализатор не создаётся. Прокси окружения не используются. |
| `FORTE_VLM_KEY_FILE` | — | Файл с ключом, уходит как `Authorization: Bearer` |
| `FORTE_VLM_MODEL` | `local` | Имя модели на сервере |
| `FORTE_VLM_TIMEOUT` | `45` | Таймаут одного запроса, с |
| `FORTE_DETECTOR` | `nano` | Размер RF-DETR: `nano`, `small` или `medium` |
| `FORTE_VISION_RESERVE_SEC` | `20` | Запас до дедлайна на кадры-доказательства и правила |
| `FORTE_ANCHORED_CACHE`, `FORTE_ANCHORED_TRACE` | пусто | Только для офлайн-оценки: кеш ответов модели на диске и подробный след по ролику. В проде не задаются. |

`FORTE_VLM_BACKEND`, `FORTE_VLM_FALLBACK_MODEL`, `FORTE_VLM_RETRY_SEC`, `FORTE_VISION_PROFILE` и `FORTE_LOCAL_AUDIT_DIR` читает только прежний анализатор `forte_vision.backend_adapter:create_analyzer`. Это наблюдатель `observer.py`: модель через MLX или OpenAI-совместимый сервер с запасной MLX. Его описывает [vision/README.md](../vision/README.md). Он остаётся в коде и тестах, в проде не используется.

## Офлайн-замер

Тот же путь, что у worker (`_analyze_job`), но без HTTP и очереди. Ролики берутся из `../data/raw/open/videos` относительно корня репозитория:

```sh
PYTHONPATH=.:decision:vision/src python vision/tools/anchored_eval.py \
  --factory forte_vision.anchored.analyzer:create_analyzer --videos holdout --out RESULTS
python -m data_tools.score_videos RESULTS
```

`score_videos` код решения не импортирует. Эталон — `../data/work/team_labels.csv` вне репозитория, X-47 и X-48 по умолчанию не считаются: это копии X-4 и X-5. Результаты и разбор пропусков — [SUBMISSION.md](SUBMISSION.md) §7.1–7.2.

Независимый HTTP-evaluator `data_tools.evaluate_service` гоняет ролики через `/api/v1` поднятого сервиса. Ключ он читает из `FORTE_API_KEY`, импорт разметки описан в [data_tools](../data_tools/README.md):

```sh
python -m data_tools.evaluate_service --base-url http://127.0.0.1:8000 \
  --videos /path/videos --gold local_data/gold.json \
  --output-dir local_data/evaluation --limit 5
```

Ошибки и таймауты он считает пропусками в recall и неуспехами в accuracy. После прогона `data_tools.aggregate_failures` отделяет пропуски завершившегося анализа от положительных видео, потерянных из-за ошибки выполнения. Видео, кадры и наблюдения остаются локально.

## Проверка подключения

Тот же набор, что запускает автодеплой (`infra/mac/serve.sh`):

```sh
python -m pytest -q backend/tests decision/tests data_tools rules/test_catalog.py vision/tests
```

FFmpeg/ffprobe должны быть в PATH либо заданы в `FORTE_FFMPEG_BIN`/`FORTE_FFPROBE_BIN`. Тесты используют синтетическое видео, настоящие worker и VideoIO и заглушки вместо детектора и сервера модели. Они проверяют интеграцию, а не качество.

Docker-образ (`Dockerfile`) ставит только backend: в нём нет decision, каталога правил, vision и весов, поэтому анализатор в нём не запустится. Прод работает нативно: на Mac процессы поднимает `infra/mac/serve.sh`, модель обслуживает `llama-server` на GPU-машине команды.
