## 1. Что это

Сервис принимает запись камеры кассы в формате `.mov` и ищет на ней видимые признаки нарушения кассовой дисциплины. В ответе вердикт `violation` или `no_violation`. Для каждой находки сервис даёт тип, таймкод, 1–3 исходных JPEG-кадра, описание и пункт нормативного акта РК со ссылкой на adilet.zan.kz. Облачные AI-сервисы в обработке не участвуют: модели работают на машинах команды, в банке — на одном сервере (разделы 3.4 и 7). Результат — подсказка для проверяющего, а не юридическое заключение (раздел 7 ТЗ).

- URL сервиса: <заполнить при сдаче>
- URL API: <заполнить при сдаче> (методы `/api/v1/…`, интерактивная документация `/docs`)
- Ключ: передаётся отдельно, заголовок `X-API-Key`
- Версия: коммит `<SHA на боевом хосте>` ветки `main`; описание соответствует этому коммиту. Деплой заморожен на время прогона (`DEPLOY_FREEZE`).

## 2. Как пользоваться и как запустить

### 2.1 Веб-интерфейс

Интерфейс открывается по URL сервиса без ключа и работает через `/ui-api` в общей с API жюри очереди (`backend/app.py:132-140`, см. 6.4). Во вкладке «Проверка видео» выбрать или перетащить `.mov` до 50 МБ. После загрузки идёт «Анализ» с таймером до лимита 5 минут, статус опрашивается каждые 1,5 с. Результат:

- «Обнаружены признаки возможных нарушений» — в UI это экран «Разбор эпизодов» («Найдено эпизодов: N»). По каждому эпизоду — тип, таймкод, наблюдение, нормативное основание со ссылкой и 1–3 кадра; рядом плеер исходного файла с метками эпизодов, файл воспроизводится локально в браузере.
- «Нарушений не обнаружено. Вывод относится только к обработанному видео.»
- Статус `failed` — «Проверка не завершена». За отсутствие нарушений UI его не выдаёт.

Вкладка «Результаты» хранит последние 50 проверок в IndexedDB этого браузера (`frontend/README.md:17-29`).

### 2.2 API

Два шага: загрузка файла в поле `file`, затем опрос статуса раз в 1–2 с.

```bash
BASE='<URL API>'; KEY='<ключ>'
JOB=$(curl -fsS -H "X-API-Key: $KEY" -F "file=@video.mov" "$BASE/api/v1/analyze" \
      | python3 -c 'import sys,json; print(json.load(sys.stdin)["job_id"])')
while R=$(curl -fsS -H "X-API-Key: $KEY" "$BASE/api/v1/jobs/$JOB"); echo "$R" | grep -q '"processing"'; do sleep 2; done
echo "$R"
```

Варианты ответа (`backend/contracts.py:28-57`):

- `{"job_id":"…","status":"processing"}` — задание в очереди или в работе.
- `{"job_id":"…","status":"failed"}` — анализ не завершён. Код причины (`deadline_exceeded`, `analysis_incomplete`, `model_crashed` и т. п.) хранится только во внутренней базе сервиса и в ответ не попадает. `failed` не означает «нарушений нет».
- `{"job_id":"…","status":"done","verdict":…,"violations":[…]}` — анализ завершён; вердикт всегда согласован со списком нарушений.

Пример формата ответа: собран по шаблону правила `KZ_NBK_231_P12_PERSONAL_ITEMS`, это не эталонный случай; кадр сокращён.

```json
{"job_id": "…", "status": "done", "verdict": "violation",
 "violations": [{
   "type": "Личные вещи на рабочем месте кассира",
   "timecode_sec": 2.066667,
   "description": "На кассовом столе лежат личные вещи (верхняя одежда, сумка). Норма: личные вещи работников хранятся вне кассового узла. Это признак возможного нарушения; вывод проверяет человек.\nНормативное основание: Правила осуществления кассовых операций и операций по инкассации, постановление Правления НБРК от 29.11.2019 № 231 — Личные вещи на рабочем месте кассира; Пункт 12, абзац 1 (ID: KZ_NBK_231_P12_PERSONAL_ITEMS). https://adilet.zan.kz/rus/docs/V1900019680",
   "evidence_frames": [{"timestamp_sec": 2.066667, "image_base64": "/9j/4AAQ…"}]}]}
```

Поля нарушения:

- `type` — одно из названий каталога `rules/cash_checks.json`, дословно как в разделе 5; на практике 13 из 14, KEYS пока не выдаётся.
- `timecode_sec` — время кадра-доказательства, ближайшего к главному моменту события (`backend/worker.py:250`).
- `evidence_frames` — 1–3 настоящих кадра файла по их реальному PTS, JPEG в base64 без префикса `data:`.
- `description` — шаблон правила и строка «Нормативное основание: документ — правило; пункт (ID). URL» (`backend/worker.py:252-254`). Если видео проанализировано не целиком, добавляется: «Анализ завершён не по всему видео: нарушение найдено на проверенной части, остальные фрагменты не проверены.»

Коды HTTP (`backend/app.py:58-96`, `backend/service.py:39-82`):

| Код | Когда |
|---|---|
| 401 | нет ключа или ключ неверный |
| 503 без `Retry-After` | ключ жюри на сервере не настроен |
| 422 | в запросе нет поля `file` |
| 415 | имя файла не оканчивается на `.mov` (содержимое проверяется уже при анализе; битый файл даёт `failed`) |
| 413 | файл больше 50 МБ |
| 400 | пустой файл или некорректный `Content-Length` |
| 408 | загрузка не уложилась в срок |
| 503 + `Retry-After: 5` | в работе и очереди уже 5 заданий |
| 404 | нет такого `job_id` |

Срок — 300 с с момента прихода запроса, в него входят загрузка, очередь и анализ (`backend/service.py:33`, `backend/config.py:19`).

### 2.3 Как запустить

Подробности — `infra/mac/README.md`, шаблон настроек — `infra/mac/mac.env.example`.

**Что нужно.** Mac на Apple Silicon с 16 ГБ (пик MLX — 9,4 ГБ, `vision/README.md:68-75`), Python 3.12, `uv`, `ffmpeg`, `ffprobe`. Для основной модели — GPU-машина с llama.cpp `llama-server` (Qwen3-VL-8B-Instruct GGUF Q4_K_M и mmproj, только `127.0.0.1:8080`, `infra/mac/README.md:21`). Веса скачиваются заранее, обработка видео интернета не требует.

**Установка** — одно окружение для backend, decision и vision; команды восстановлены по окружению ночного прогона, установка с нуля по ним не проверялась (НЕ ПРОВЕРЕНО). Дальше `uv sync` — только с `--inexact`, иначе uv удалит пакеты backend и поставит pillow 13, а backend требует `Pillow<13` (`pyproject.toml:16`).

```bash
(cd vision && uv sync --extra mlx --extra detector)
uv pip install --python vision/.venv/bin/python -c requirements.lock -e . -e ./decision
```

**Настройки.** Скопировать `mac.env.example` в каталог вне git и заполнить. Ключ жюри — `python -c "import secrets; print(secrets.token_urlsafe(32))"`; в режиме `production` ключ короче 32 символов не принимается (`backend/config.py:63-67`). Добавить `export FORTE_PUBLIC_API_KEYS=false` (раздел 7). Переменные `FORTE_VLM_*`, `FORTE_RULE_CATALOGS`, `FORTE_DETECTOR`, `FORTE_VISION_PROFILE` читаются только из окружения процесса, а не из `.env` (`vision/src/forte_vision/vlm.py:321-341`; вывод из кода, запуском не проверено).

**Запуск.** `infra/mac/serve.sh <mac.env>` поднимает SSH-туннель, API на `127.0.0.1:8000` и worker и перезапускает их при падении. Вручную (без `serve.sh` туннеля нет: с `FORTE_VLM_URL` из примера задания считаются на локальной MLX):

```bash
# в каждом из двух терминалов, из корня репозитория:
source ../local_data/mac.env; export PYTHONPATH="$PWD:$PWD/decision:$PWD/vision/src"
"$FORTE_PYTHON" -m uvicorn backend.app:app --host 127.0.0.1 --port 8000   # терминал 1
"$FORTE_PYTHON" -m backend.worker                                        # терминал 2
curl -i http://127.0.0.1:8000/health/ready                               # 200 и "status":"ready"
```

`/health/ready` = 200, если доступна БД, найдены ffmpeg и ffprobe, подключены настоящие адаптеры, heartbeat worker моложе 10 с и модель загружена (`backend/app.py:146-160`); доступность `llama-server` она не показывает. `Dockerfile` и `compose.yaml` для анализа пока не годятся (раздел 7).

## 3. Архитектура и подход

```
Жюри: POST /api/v1/analyze (X-API-Key)      Браузер: POST /ui-api/analyze
               └──────────────┬──────────────────┘
API (FastAPI): ключ до разбора файла · .mov · ≤50 МБ · fsync+sha256 · дедлайн = приход + 300 с
Очередь SQLite (WAL): queued → running → done | failed · ≤5 заданий · просроченные → failed
Worker-супервизор: FIFO · делит время между заданиями очереди · kill процесса модели на дедлайне
Процесс модели (грузится при старте и заново после kill или падения;
                время перезагрузки идёт из бюджета следующего задания, не измерено):
  VideoIO (ffprobe/ffmpeg): все PTS, проверка декодирования, исходные JPEG
  1. таймлайн: окна по 8 кадров → VLM → шаги из словаря 26 событий
  2. чек-лист (код): 13 проверок порядка и пропуска шагов
  3. перепроверка: 6 плотных кадров → VLM: yes / no / unclear
  4. правила rules/cash_checks.json: предикат → тип, документ, пункт, URL
  worker: проверка PTS · 1–3 JPEG · таймкод · описание + норма
GET /api/v1/jobs/{id} → processing | failed | done
```

### 3.1 Подход

Большинство нарушений кейса — бездействие или нарушенный порядок: деньги приняты, а показа документа в кадре нет; кассир ушёл, не заблокировав экран; сумку убрали в сейф без видимого пересчёта. По одному кадру этого не увидеть, поэтому сервис строит последовательность действий по всему ролику.

- **VLM наблюдает, решает код.** Модель отмечает видимые шаги из фиксированного словаря в 26 событий (`vision/src/forte_vision/timeline.py:21-48`) и отвечает «да/нет/неясно» на узкие вопросы перепроверки. Тип, норму и вердикт выбирают код и каталог правил. Реальные PTS кадров передаются в запросе, модель отвечает в тех же секундах; температура 0 (`vlm.py:98, 205`).
- **Чек-лист.** 13 детерминированных проверок по таймлайну, у каждой один предикат (`timeline.py:51-65, 162-267`). Для нарушения по бездействию таймкод — момент, когда шаг должен был случиться; ТЗ оставляет этот выбор команде (FAQ 10).
- **Перепроверка.** На каждую находку — узкий вопрос по 6 плотным кадрам (`observer.py:498-542`). «Нет» снимает находку; «неясно» или нехватка времени её оставляют: пропуск хуже ложного срабатывания (FAQ 16). Для LOCK, LEAVE, SAFE, DOOR и DOC вопрос задаётся и тогда, когда чек-лист промолчал, но на таймлайне есть ключевое событие. Нарушение добавляется только при явном ответе, который его подтверждает: «да», а для DOC «нет» на вопрос «показан ли документ». «Неясно» его не добавляет.
- **Норма — только из каталога.** Нарушение, для которого нет правила, не выдаётся.
- **Кадры-доказательства** — до 3 кадров из тех, что модель реально видела, ближайших к моменту события. Worker сверяет каждый PTS со списком ffprobe с точностью 1e-6 и извлекает JPEG именно этого кадра (`backend/worker.py:188-192, 210-216`).

Детектор RF-DETR в сервисном пути только вырезает стол (`dining table`) для перепроверки FOOD и ITEMS (`timeline.py:320-322`). Профили с рамками людей и ролей (`legacy_*`) сервису недоступны (`backend_adapter.py:12, 30`).

### 3.2 Бюджет 5 минут

| Шаг | Правило | Код |
|---|---|---|
| Дедлайн | приход запроса + 300 с, общий для загрузки, очереди, анализа и JPEG | `backend/service.py:33` |
| Бюджет анализа | min(до дедлайна − 20 с, доля); доля при очереди — (последний дедлайн в очереди − сейчас − 20 с) / (заданий + 1) − 8 с, не меньше 30 с | `backend/worker.py:175-185`, `vision/…/backend_adapter.py:209-214` |
| Окна таймлайна | max(8 с, длительность/8), по 8 кадров, длинная сторона ≤ 960 px; если не помещаются в 0,6 бюджета, расширяются (минимум 2 окна, в профиле `fast` максимум 8) | `observer.py:50-54, 65, 428-446` |
| Оценка вызова | 12 с для сервера, 30 с для MLX, после трёх замеров 1,25 × средняя; вызов, который не успевает, не начинается, окно помечается непокрытым | `vlm.py:20-22, 303-317`, `observer.py:451-485` |
| Таймаут вызова | сервер модели: min(`FORTE_VLM_TIMEOUT`, остаток бюджета), 45 с в `mac.env`, 60 с по умолчанию; при остатке < 3 с вызова нет. Вызов MLX не прерывается, его ограничивают проверка перед стартом и kill на дедлайне | `vlm.py:170-176, 285-286` |
| Жёсткий предел | kill процесса модели на дедлайне; запоздавший результат база не примет | `worker.py:481-485`, `store.py:190-196` |

### 3.3 Отказоустойчивость

- **Проверка при старте.** Процесс модели загружает анализатор и каталог, проверяет каталог пустым прогоном движка правил (`decision/forte_decision/backend_adapter.py:52-60`) и сверяет, что все 13 предикатов анализатора покрыты правилами. Если нет, `/health/ready` отвечает 503, а задания получают `failed`, а не тихий `no_violation` (`worker.py:37-44, 292-302`). Саму VLM эта проверка не вызывает.
- **Резервная модель** (режим `FORTE_VLM_BACKEND=openai+mlx`, `mac.env.example:17`). Перед каждым заданием сервис делает `GET /health` к серверу модели с таймаутом 2 с. Если сервер нездоров или упал внутри задания, задание до конца считается на локальной MLX (`vlm.py:236-300`).
- **Неполный анализ.** Если окно не покрыто, нарушение чек-листа, вывод которого опирается на это окно, не выдаётся (`timeline.py:263-267`). Находки, подтверждённые прямым вопросом перепроверки, выдаются и в этом случае (`observer.py:534-542`). Дальше (`worker.py:220-229`): найденные нарушения выдаются с пометкой о неполном анализе; нет находок, но покрыто больше нуля окон — `no_violation`; не покрыто ничего — `failed`.
- **Падение worker.** Задание возвращается в очередь, попыток не больше 3, дедлайн не сдвигается (`store.py:223-238`).
- **Ответы модели.** Исключение VLM делает окно непокрытым, задание продолжается; ответ не в JSON переспрашивается один раз (`observer.py:451-485`).

### 3.4 Локальность

Что обеспечено в коде:

- Адрес сервера модели — только localhost, частная сеть или `*.local`; прокси окружения отключены (`vlm.py:151-168`).
- Веса VLM загружаются только из локального кеша: `local_files_only`; `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1` выставляются, если не заданы иначе (`vlm.py:61-68`, `backend_adapter.py:180-181`). Веса RF-DETR (`rf-detr-nano.pth` в `~/.roboflow/models` или `$RF_HOME`) нужно положить заранее: если файла нет, rfdetr при старте скачивает его с storage.googleapis.com (`rfdetr/detr.py:682-704`).
- FFmpeg читает только `file`/`pipe` и формат `mov`; звук, субтитры и data-потоки отброшены (`backend/video_io.py:220-222, 270-275, 303-309`).
- UI ничего не загружает с CDN. Лица не распознаются, звук не анализируется.

Сегодняшняя топология:

- Сервис работает на MacBook, модель — на ноутбуке участника команды с RTX 4060; адрес модели `127.0.0.1:18080` (`infra/mac/mac.env.example:19, 26-31`).
- Кадры идут с Mac на ноутбук через VPS команды двумя SSH-туннелями. Участки Mac→VPS и VPS→ноутбук шифрует SSH, а на самом VPS кадры проходят через его локальный порт 18080 обычным HTTP.
- Видео жюри тоже приходят через этот VPS: публичный адрес → VPS → обратный туннель `-R 127.0.0.1:18000` → API на Mac (`infra/mac/serve.sh:47-48`). Настройка TLS на VPS в репозитории не описана (НЕ ПРОВЕРЕНО).
- Облачные AI-сервисы не используются: VPS только пересылает трафик. Проверка адреса такой туннель от локального сервера не отличает; в банке этого звена нет (раздел 7).

В ответе API № 231 назван короче, как в каталоге. Утратившие силу Закон РК № 2444 и постановление НБРК № 48 не цитируются: это проверяет тест `test_no_citations_of_repealed_acts` (`rules/test_checks_catalog.py:58-62`); поиском по репозиторию других ссылок на них нет.

**Сопоставление.** Проверка чек-листа (3.1) выставляет свой предикат в `observed`; правило `rules/cash_checks.json` с этим предикатом становится нарушением и даёт тип, документ, пункт, URL и шаблон описания. У каждого из 14 правил один обязательный предикат (`rules/cash_checks.json`, тест `rules/test_checks_catalog.py:31-36`). Для нарушений по бездействию (DOC, LOCK, AUTH, REG, BAG) описание говорит «в кадре не видно…», а не «не сделано»; для остальных описано видимое состояние. «По смыслу» — прямого требования в пункте нет, применение — трактовка команды; где привязка целиком по смыслу, это написано и в описании.

**Типы нарушений:** код и строка `type` дословно, как в ответе API; ниже — что видно · норма · привязка. Нормы — Правила № 231, если не указано иное.

1. **DOC** — «Приём денег без документа, удостоверяющего личность клиента»
   До приёма денег не видно показа документа (цифровой допустим) · п.19 пп.1 · прямо. Проверка срабатывает и на приём сумки; если сумку передаёт инкассатор, п.19 пп.1 неприменим (порядок — п.24), и находку надо снимать. Пример — ложный DOC на чистом X-14.
2. **MIX** — «Деньги предыдущего клиента не убраны в сейф и смешаны с деньгами следующего»
   Следующий клиент обслуживается, пока деньги предыдущего лежат на столе, или деньги разных клиентов складываются вместе · п.20 абз.2 · прямо.
3. **LOCK** — «Уход с рабочего места без блокировки компьютера»
   Кассир уходит, на экране рабочий стол или программа, экрана блокировки не видно · п.2 пп.17, п.80; в описании также АРРФР № 53 п.71 пп.9 · по смыслу.
4. **LEAVE** — «Уход с рабочего места с неубранными в сейф деньгами или документами»
   Кассир уходит, наличные или документы остаются на столе · п.20 абз.2, п.80 · по смыслу.
5. **SAFE** — «Сейф оставлен открытым»
   После работы с сейфом дверца остаётся открытой · п.20 абз.2 · по смыслу.
6. **KEYS** — «Ключи оставлены в замке сейфа»
   После закрытия сейфа ключ остаётся в замке · п.80 · по смыслу. Правило в каталоге есть, анализатор его пока не выдаёт.
7. **DOOR** — «Дверь кассы оставлена открытой»
   Кассир в кассе, дверь кассы открыта · № 14 п.8, п.16 пп.1 (п.16 приостановлен до 01.01.2027 и на этот период действует в редакции, приведённой в постановлении) · по смыслу.
8. **NOCLIENT** — «Пересчёт денег без клиента: клиент ушёл до завершения операции»
   Клиент передаёт деньги и уходит, пересчёт идёт без него · п.20 абз.1 · прямо.
9. **ITEMS** — «Личные вещи на рабочем месте кассира»
   На кассовом столе лежат личные вещи (верхняя одежда, сумка) · п.12 абз.1 · прямо.
10. **FOOD** — «Еда и напитки на рабочем месте кассира»
    На кассовом столе еда или напитки · п.12 абз.1 · по смыслу.
11. **AUTH** — «Купюры не проверены на счётной машине или детекторе»
    Купюры пересчитаны вручную, пропуска через счётную машину или детектор не видно · п.19 пп.2, п.9 · прямо (требование проверки подлинности). Проверку вне кадра запись не исключает, это сказано в описании.
12. **REG** — «Деньги из сумки убраны в сейф без видимого пересчёта и внесения в учёт»
    Деньги из сумки убираются в сейф, между этими шагами не видно пересчёта и работы с компьютером или документами · в ответе п.19 пп.2 и 4, п.24 пп.2 · п.19 пп.2 прямо для денег клиента; для целой сумки от инкассации пересчёт не обязателен (п.25), поэтому по смыслу. Строка `type` упоминает учёт, но регистрация (п.24 пп.2) и сверка (п.19 пп.4) по видео не устанавливаются; про регистрацию это сказано в описании.
13. **BAG** — «Сумка с деньгами оставлена на столе без пересчёта»
    Сумка с деньгами остаётся на столе, пересчёта не видно · п.19 пп.2, п.20 абз.2 · прямо для денег клиента, для сумки от инкассации — по смыслу (целую сумку пересчитывать не требуется, п.25).
14. **QUE** — «Обслуживание клиента вне очереди»
    Обслуживается подошедший позже, ранее пришедший ждёт · АРРФР № 91 п.9 пп.5 · по смыслу. Есть ли у клиента право на внеочередное обслуживание, по видео не определяется.

### 6.5 Что не видно в ответе и чего сервис не утверждает

- **Неполный анализ без находок.** `no_violation` при неполном анализе через API и UI не отличить от полного: `partial_result` и `coverage` пишутся только во внутреннюю диагностику (`backend/contracts.py:48-57`). Порог — хотя бы одно покрытое окно: `no_violation` может опираться на 1 окно из 8. Под нагрузкой это реально: в залпе X-14 получил `no_violation` по половине окон.
- **Описание шаблонное** — текст правила, одинаковый для всех случаев типа. Конкретная причина срабатывания, шаги таймлайна и ответы перепроверки в ответ не попадают. Сохраняются они только в локальном аудите, если задан `FORTE_LOCAL_AUDIT_DIR` (`vision/src/forte_vision/audit.py:10-13`).
- **Одна находка на проверку.** Повторный случай того же типа в ролике в ответ не попадёт (`timeline.py:162-267`).
- **Закрытый список.** Сервис ищет только 13 проверок; типы, которых нет в обучающих данных (FAQ 9), он не найдёт.
- **Невидимое на видео не утверждается.** Сервис не делает выводов о проводках, регистрации суммы, сверке и праве клиента на внеочередное обслуживание (оговорка к строке `type` REG — в разделе 5). Телефон в кассе не флагуется: п.12 абз.2 № 231 допускает средства связи без фото- и видеофиксации, по видео это не определить (`rules/README.md:41-44`).
- **Нет цитат в UI.** Карточка «Основание» показывает документ, пункт и ссылку без дословной цитаты: в `frontend/dist/norms.js` цитаты есть только для двух старых `rule_id`, которых нет в текущем каталоге.

### 6.6 Как получены эталон и цифры

- Вердикт и секунда эталона даны организаторами, тип — по разметке команды (`team_labels.csv`; в 6.2 — `human_labels_v2.md`). Неуверенные метки — X-15 и X-30, спорная — X-37.

Кадры X-22…X-48 открытого обучающего набора при разметке просматривала облачная сессия Claude — как инструмент разработки, с разрешения команды (`scenario-catalog-draft.md:7-8`). Эталонные метки — метки команды; Claude был вспомогательным инструментом.
- Ракурсы A–D всех 42 роликов (столбец `camera_claude` в `eval_truth.csv`) взяты из каталога сценариев, который облачная сессия Claude составила по кадрам (инструмент разработки); отдельно их не перепроверяли.
- В обработке видео сервисом облачных моделей нет.

## 7. Целевая установка в контуре банка

**Топология.** Один on-prem GPU-сервер: на нём API, worker и сервер модели; туннелей и VPS нет. Модель работает за OpenAI-совместимым endpoint (llama-server или vLLM). Настройки: `FORTE_VLM_BACKEND=openai`; `FORTE_VLM_URL` — `http://127.0.0.1:8080`, IP из частной сети или имя `*.local` (другое DNS-имя код отклонит, `vlm.py:151-157`); `FORTE_VLM_MODEL` — имя модели на сервере; ключ к серверу модели — из файла `FORTE_VLM_KEY_FILE`.

**Офлайн-веса.** Заранее разложить Qwen3-VL-8B-Instruct GGUF и mmproj, кеш HF (`HF_HOME`) с флагами `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1` и веса RF-DETR `rf-detr-nano.pth`: без этого файла rfdetr при старте пойдёт в интернет (3.4).

**Приватный ключ.** `FORTE_ENVIRONMENT=production` и `FORTE_API_KEY` не короче 32 символов. Обязательно `FORTE_PUBLIC_API_KEYS=false`: по умолчанию флаг `true`, и тогда `GET /ui-api/key` отдаёт общий ключ любому посетителю, а `/api/v1` его принимает (`backend/config.py:31`, `backend/app.py:33-40, 125-130`).

**Ретенция**

- Видео удаляется после перехода задания в `done` или `failed`: worker проходит по завершённым заданиям раз в секунду (`purge_uploads`, `backend/worker.py:450-470, 487-489`).
