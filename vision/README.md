# vision — локальный VLM-наблюдатель

**В проде работает другой анализатор:** `FORTE_ANALYZER_FACTORY=forte_vision.anchored.analyzer:create_analyzer`
(`src/forte_vision/anchored/`). RF-DETR nano находит моменты, Qwen3-VL-8B на `llama-server` отвечает на узкие
вопросы по увеличенным вырезкам; MLX, `FORTE_VLM_BACKEND` и профили он не использует. Описание —
[docs/SUBMISSION.md](../docs/SUBMISSION.md), раздел 3, и [docs/ml-integration.md](../docs/ml-integration.md).

**Всё, что ниже, — прежний анализатор (observer, `forte_vision.backend_adapter:create_analyzer`).** Он остаётся
в коде, но в проде не используется, и текст под новую схему не переписывался.

Видео кассы (.mov) → наблюдения для правил. Vision только наблюдает: кандидаты-интервалы,
кадры-доказательства по реальным PTS и предикаты `observed / not_observed / unclear`. Тип нарушения,
норму и вердикт решают `decision/` и `rules/`. Всё работает локально, сеть при обработке не нужна
(веса только из локального кеша, `HF_HUB_OFFLINE=1`). Лица не распознаются, звук не используется.

## Запуск

```bash
cd vision
uv sync --extra mlx --extra detector --extra dev   # мак (Apple Silicon); на Linux+NVIDIA: --extra cuda
uv run pytest -q                                   # синтетическое видео + заглушки, реальные данные не нужны
uv run forte-vision observe video.mov --profile fast --backend mlx --detector nano \
    --model mlx-community/Qwen3-VL-8B-Instruct-4bit --out obs.json --diag diag.json
```

Подключение к backend: `FORTE_ANALYZER_FACTORY=forte_vision.backend_adapter:create_analyzer`
(переменные `FORTE_VLM_BACKEND`, `FORTE_VLM_MODEL`, `FORTE_DETECTOR`, `FORTE_VISION_PROFILE`,
`FORTE_VISION_RESERVE_SEC` — см. `backend_adapter.py`). Веса скачиваются заранее; на маке только
нативно — Docker на macOS не видит Metal.

## Конвейер

1. **Сцена** (`scene.py`, RF-DETR N/S/M): стол, «место кассира» (где дольше всего находится человек
   у стола — без трекинга по ID и без лиц), присутствие людей и предметов → события: уход с места
   кассира, смена числа людей, предмет на столе.
2. **Движение** (`motion.py`): энергия изменений 5 кадр/с по каналам RGB — в зоне стола (из сцены)
   и, с меньшим весом, по всему кадру.
3. **Скрининг VLM**: всё видео редкой выборкой, перекрывающимися окнами, открытый список категорий
   + `other_suspicious`.
4. **Объединение**: источники не фильтруют друг друга; согласие источников повышает приоритет;
   кандидат не длиннее `max_candidate_sec`.
5. **Отбор под бюджет**: лучший кандидат в каждом отрезке времени, затем по приоритету с минимальным
   разнесением.
6. **Перепроверка**: кадры полного разрешения; копии для VLM — с рамками ролей
   (зелёная CASHIER / оранжевая PERSON); один вопрос на все предикаты и видимость → JSON.
   Кадры-доказательства в выходе — оригинальные, без рамок.

Честное покрытие: не успели пройти всё видео скринингом — `coverage_complete=false`, `partial`;
отобранный кандидат не перепроверен — `partial`, его предикаты пустые (= `unclear`). Битый файл → `failed`.

## Контракты

- `contract.py` — строгий валидатор Observation (формат decision/), лишние поля запрещены.
- `backend_adapter.py` — `ObservationBatch` backend: времена событий только из `frame_pts`
  переданного VideoIO; именованные tri-state видимости — в `observations` под своими именами,
  поле `visibility` (clear/partial/unusable) не заполняется — это другое утверждение.
- Оценки, модель, ревизия весов, профиль и тайминги — только в diagnostics, без содержания кадров.

## Оценка механизма кандидатов

`tools/candidate_recall.py` — попадает ли размеченная секунда нарушения (±1 с) в отобранного кандидата.
Печатает только агрегаты; разметка и видео — локально, вне репозитория.

Первый замер на открытой выборке (42 ролика, 22 с нарушением), без VLM, профиль fast (бюджет 8 перепроверок):

| Источники | Попаданий | Покрыто видео (медиана, с нарушением) | Ожидание при случайной расстановке того же покрытия |
|---|---|---|---|
| движение по всему кадру | 14/22 | 34% | ≈ 8 |
| детектор сцены + движение в зоне стола | 20/22 (детектор 18, движение 15) | 74% | ≈ 16 |

Рост полноты во втором варианте в основном объясняется тем, что бюджет перепроверок используется
целиком (на коротких роликах это почти всё видео); выигрыш над случайной расстановкой — сопоставимый.
Ошибка главной секунды у попаданий — медиана 1.2 с. Без VLM на ролик уходит медиана 3.2 с (макс 18 с).
Это полнота кандидатов, а не качество итогового вердикта.

## Замеры (M1 Pro 16 ГБ, MLX 4 бит, ролик ~142 с)

| | Qwen3-VL-8B | Qwen3.5-9B |
|---|---|---|
| перепроверка, 4 кадра 464x848 | 13.4 с | 14.4 с |
| глобально 0.5 кадр/с (72 кадра 224x416) | 67 с | 60 с |
| глобально 1 кадр/с (143 кадра) | 147 с | 120 с |
| пик памяти | 9.4 ГБ | 9.3 ГБ |

RF-DETR при 5 кадр/с, MPS: Nano 44 мс/кадр, Small 60, Medium 73. Декод ролика целиком — ~1.3 с.
На маке полный профиль в бюджет не укладывается; fast-профиль на длинных роликах — на грани.

## Модель на GPU-машине

`FORTE_VLM_BACKEND=openai+mlx`: запросы к модели идут на OpenAI-совместимый сервер (llama.cpp `llama-server`,
MIT, с официальным `Qwen/Qwen3-VL-8B-Instruct-GGUF` Q4_K_M, Apache-2.0) на ноутбуке с RTX 4060 8 ГБ через
SSH-туннель; адрес — только localhost или частная сеть. Если сервер недоступен или ответ битый, запрос сразу
уходит локальной MLX-модели Mac, а сервер не трогаем `FORTE_VLM_RETRY_SEC` секунд. Счётчики
`vlm_primary_calls / vlm_fallback_calls / vlm_primary_failures` — в diagnostics.

Замер: ролик ~142 с, профиль fast — 65–79 с на RTX 4060 (модель 31 с на 16 запросов) против 150–250 с
целиком на M1 Pro.

## Ограничения

- Короткие действия руками дают слабое движение на фоне ходьбы людей; зона стола и детектор частично
  это компенсируют, но полнота кандидатов — главный риск, измеряется `candidate_recall.py`.
- VLM может путать роли людей; рамки ролей от детектора — подсказка, а не истина.
- «Место кассира» предполагает одного кассира и фиксированную камеру в пределах ролика.
- `TransformersBackend` (CUDA) не проверялся на GPU-хосте.
