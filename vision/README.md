# vision — локальный VLM-наблюдатель

Видео кассы (.mov) → **Observation** для `decision/`. Vision только наблюдает: кандидаты-интервалы,
кадры-доказательства по реальным PTS и предикаты `observed / not_observed / unclear`. Тип нарушения,
норму и вердикт решают `decision/` и `rules/`. Всё работает локально, сеть при обработке не нужна
(веса только из локального кеша, `HF_HUB_OFFLINE=1`). Лица не распознаются, звук не используется.

## Запуск

```bash
cd vision
uv sync --extra mlx --extra dev        # мак (Apple Silicon); на Linux+NVIDIA: --extra cuda
uv run pytest -q                       # синтетическое видео + заглушка VLM, реальные данные не нужны
uv run forte-vision observe ../path/video.mov --profile fast --backend mlx \
    --model mlx-community/Qwen3-VL-8B-Instruct-4bit --out obs.json --diag diag.json
```

Веса скачиваются заранее (`huggingface_hub.snapshot_download`), при обработке берутся только локально.
На маке — только нативно: Docker на macOS не видит Metal.

## Конвейер

1. **Движение** (`motion.py`): энергия изменений между кадрами 5 кадр/с по каналам RGB, top-K пиков.
2. **Скрининг VLM** (`observer.py`, `predicates.SCREEN_CATEGORIES`): всё видео редкой выборкой,
   перекрывающимися окнами, открытый список категорий + `other_suspicious`.
3. **Объединение**: источники не фильтруют друг друга; кандидат не длиннее `max_candidate_sec`.
4. **Перепроверка**: кадры полного разрешения, один вопрос на все предикаты и видимость → JSON.

Честное покрытие: не успели пройти всё видео скринингом — `coverage_complete=false`, `partial`;
кандидат не перепроверен — его предикаты пустые (= `unclear`). Битый файл → `failed`.

## Контракт

`src/forte_vision/contract.py` — строгий валидатор формата, согласованного с decision/
(лишние поля запрещены). Оценки, модель, ревизия весов, профиль и тайминги — только в diagnostics.
`source` кандидата — имена источников через «+» (`motion+vlm`). `frame_id` = `pts_<мс>`.

## Замеры (M1 Pro 16 ГБ, MLX 4 бит, ролик 142.4 с)

| | Qwen3-VL-8B | Qwen3.5-9B |
|---|---|---|
| перепроверка, 4 кадра 464x848 | 13.4 с | 14.4 с |
| глобально 0.5 кадр/с (72 кадра 224x416) | 67 с | 60 с |
| глобально 1 кадр/с (143 кадра) | 147 с | 120 с |
| пик памяти | 9.4 ГБ | 9.3 ГБ |

RF-DETR при 5 кадр/с, MPS: Nano 44 мс/кадр, Small 60, Medium 73. Декод ролика целиком — 1.25 с.

Сквозной `observe --profile fast` с Qwen3-VL-8B: ролик 26 с — 119 с, ролик 142 с — 249 с и `partial`
(не хватило перепроверок). **На маке fast-профиль пока не укладывается в бюджет на длинных роликах.**

## Известные проблемы (первый прогон на 2 роликах, не оценка качества)

- Короткое действие руками у стола может не попасть в кандидаты: пики движения забирает ходьба
  людей, а скрининг 0.5 кадр/с короткое событие пропускает. Нужно: движение по зоне стола/рук,
  а не по всему кадру; гарантированное равномерное покрытие перепроверками.
- Нарезка длинных интервалов скрининга даёт слишком много кандидатов на длинном ролике. Нужен
  отбор с разнесением по времени и/или слияние соседних кусков одной категории.
- VLM путает роли (входящий клиент ↔ уходящий кассир). Нужны детектор + трекер ролей
  (RF-DETR N–L, Apache-2.0; ассоциация ByteTrack без весов CrowdHuman) как ещё один источник.
- `TransformersBackend` (CUDA) написан, но не запускался — проверить на GPU-хосте.
