# Нормативные источники и типы нарушений

Каталог по умолчанию — `cash_checks.json`: одно правило на проверку, у каждого один предикат `required`. Сервис грузит его, если `FORTE_RULE_CATALOGS` не задан (`decision/forte_decision/backend_adapter.py`). При старте модели worker проверяет, что каждый предикат анализатора есть в каталоге: иначе модель не готова и `/health/ready` не зелёный. Каталог может содержать правила, которые анализатор пока не отдаёт (KEYS).

Результат — признак возможного нарушения для проверки человеком, а не юридическое заключение. Тексты пунктов сверены с действующими редакциями на adilet.zan.kz 17–18.10.2026.

## Ограничения

- DOC срабатывает и на приём сумки; если её передаёт инкассатор, п.19 пп.1 неприменим (порядок — п.24), и находку проверяющий снимает.
- По видео не устанавливаются данные учётной системы: регистрация суммы, проводки, сверка. Формулировки — «в кадре не видно», а не «не сделано».
- Телефон в кассовом узле не флагуется: п.12 абз.2 допускает средства связи без фото- и видеофиксации, по видео это не определить; в Х-10 организаторы считают телефон в кармане не нарушением.
- Ключ в замке сейфа занимает 3–5 px; правило KEYS есть в каталоге, но анализатор его пока не отдаёт.
- Право клиента на внеочередное обслуживание по видео не определяется.
- `cash_receipt.json` — прежние два seed-правила по п.20 и п.22 с другими предикатами; с текущим анализатором таймлайна не совместим (проверка на старте его отклонит).

## Как добавить правило

Точный источник и пункт по действующей редакции, «по смыслу» в `source_paragraph` и в описании, если прямого требования нет, предикат с описанием наблюдения, контрпример без нарушения. Поля в пределах контракта backend (`test_fields_fit_the_backend_contract`). Не отправлять видео, кадры и их описания облачным агентам.
